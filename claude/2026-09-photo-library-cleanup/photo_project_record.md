# 写真ライブラリ整理プロジェクト 記録

対象: `OneDrive\Document\画像`
実行環境: 実家のPC上の Claude Code
期間: 2026年9月17日(木) 〜 9月20日(日)

---

## 1. 概要

OneDrive上に長年蓄積されてきた写真・動画関連ファイル(合計88,256件、約297GB)を対象に、以下を実施した。

- 重複ファイルの検出・統合(バイト単位ハッシュ照合による安全な削除)
- 撮影機種(カメラ・スマートフォン)ごとのフォルダへの再編成
- Claude Vision API(Sonnet 5)による写真内容の自動タグ付け(EXIF/XMPへの書き込み)
- 旅行・イベント単位の情報をキーワードタグとして保持(フォルダ構造は機種別に統一しつつ検索性を確保)
- 付随して発覚した OneDrive 同期先フォルダの二重化(Cドライブの `%USERPROFILE%\OneDrive` とDドライブの `OneDrive`)の解消

最終結果: 88,256ファイル・297.63GB → **74,126ファイル・252.53GB**に整理(ファイル数で約16%、容量で約45.10GB=約15%削減)。19の機種別フォルダ + 3つの受け皿フォルダ(`_機種不明`, `_非写真`, `_隔離`)に集約。

---

## 2. 背景・目的

- 音楽ライブラリ(`OneDrive\My_music`)の整理をClaude Codeで行った経験を踏まえ、同様の手法を写真にも適用
- 「ファイルを複数箇所に持ちたくない」という一貫した方針のもと、重複排除を最優先課題とした
- 単純な年別・機種別フォルダ分けだけでなく、AIによる写真内容の自動タグ付けも組み合わせることを決定

---

## 3. 設計方針(確定事項)

| 項目 | 方針 |
|---|---|
| フォルダ構成 | 機種別フォルダのみに統一(年別・日付別の細分化はしない) |
| イベント・旅行情報 | フォルダを機種別に解体する際、元のイベントフォルダ名(例: 「20230531_京都旅行」)をEXIF/XMPの Keywords フィールドにタグとして書き込み、検索で復元できるようにする |
| タグ付け方式 | Claude Vision API(Sonnet 5, Batch API)による内容自動タグ付け。写真そのものは変更せず、EXIF/XMPメタデータのみ追記 |
| 重複ファイルの扱い | 完全に1つに統合。複数箇所に同じ実体を持たない方針を徹底 |
| 安全性 | 削除は原則ごみ箱経由。写真は撮り直しがきかないため、統計的にリスクが残る場合は必ず全件ハッシュ検証してから削除 |
| RAW/HEIC等特殊形式 | 対になるJPEGが存在する場合はタグをコピー(API再送信を回避)。存在しない場合のみVision APIに送信 |
| MP3同様の教訓 | 実行前にドライラン、大量削除は事前確認、コード変更は実行中プロセスに反映されないため都度再起動 |

## 4. ロードマップ(フェーズ構成)

```
Phase 0: 事前調査・環境準備
  └ exiftool導入、iTunes/Android残骸の隔離、非写真データの隔離

Phase 1: 重複排除
  └ ハッシュ照合による完全重複の検出・削除
  └ 入れ子ミラー(丸ごと二重取込フォルダ)の発見・解消

Phase 2: AIコンテンツタグ付け(Vision API)
  ├ Tier1: JPEG等の通常画像 60,085件
  └ Tier2: RAW/HEIC/TIFF/BMP/PSD等 6,094件

Phase 3: 機種別フォルダへの再編成
  └ 年別・イベント別フォルダの解体 → 機種別フォルダへ統合
  └ イベント名のタグ化、サイドカーファイルの親追従
```

## 5. タイムライン

### 前段: OneDrive環境の整理(9/17以前〜9/20朝、断続的)
- Cドライブの `%USERPROFILE%\OneDrive`(過去のOneDrive移行時の残骸、約95,711ファイル)がDドライブの `OneDrive` と二重化していることを発見
- ハッシュ検証により、Cドライブ側にのみ存在する実データ63ファイル(2025年の旅行写真・ブログ素材)を発見し、削除前にD側へ退避
- 削除は「ごみ箱経由」を指定したが、壊れたOneDriveプレースホルダーが原因でWindowsのシェル削除が黙って完全削除にフォールバックする現象を発見(実害なし)
- 副産物として発見した失効済みGitHubトークンの安全確認も実施

### 9/17(木) 夜: プロジェクト開始・現状調査
- `OneDrive\Document\画像` の現状調査(88,256ファイル、297GB)
- フォルダ構成・重複傾向・EXIF取得率(89.5%)を把握
- ファイル名統一ルール案の策定

### 9/17〜9/18: 分類方針の確定
- 既存フォルダを「年別+イベント名(区分A)」「トップレベルのイベント名(区分C)」「年フォルダ内の入れ子イベント(区分D)」に分類
- イベント性のあるフォルダ名はタグ化、取込ログ的なフォルダ(Adobe自動生成名、DCIM標準名等)はタグ化見送りと判定
- Glenn Gould/Gipsy Kingsフォルダ相当の「丸ごと二重取込」パターン(音楽整理と同種)がここでも発見された

### Phase 1: 重複排除(9/18〜9/19)
- 全体で9,221グループ・14,641件・45.4GBが重複候補として検出
- ハッシュ検証の過程で2つの重要なリスクを発見:
  - カメラのファイル名連番がリセットされ、別年に同名・同サイズの別写真が存在するケース(836ペア中39件、4.7%が実は別写真)
  - AAEファイル(Apple編集情報)は中身が小さく偶然同サイズになりやすいため誤判定率が11.5%と高い
- 上記を踏まえ、全12,845件の未検証分も含め全件ハッシュ照合を実施(統計的リスクを許容せず、確実性を優先)
- 確定重複を削除し、写真データを保全

### Phase 2 Tier1: 通常画像60,085件のタグ付け(9/18 17:02〜9/20 3:37、約34.6時間)
- 1,000件バッチで本体処理を実施 → 50,955件完了、8,950件が通信エラーでリトライ対象に
- リトライ第1弾(1,000件バッチ):9バッチ全て100%失敗。原因調査の結果、1バッチ約200MBという大容量ペイロードが真因と判明
- リトライ第2弾(200件バッチに縮小):8,948/8,950件成功、通信エラー0件で解消
- 個別対応が必要だった182件(ゼロバイト・拡張子偽装・真の破損JPEG等)を精査し、実際に救済できた28件を修復・タグ付け完了
- Tier1最終: 59,932/60,085件(99.75%)完了

### Phase 2 Tier2: RAW/HEIC/TIFF/BMP/PSD 6,094件のタグ付け(9/20 8:06〜15:17)
- 対になるJPEGがある3,089件はタグコピーのみで対応(API再送信不要、コスト削減)
- 対になるJPEGがない3,005件をVision APIへ送信
- HEIC(pillow-heif導入によるJPEG変換)、RAW(埋め込みJPEGプレビュー抽出)の技術検証を実施した上で本格実行
- exiftoolのBMP書き込み非対応が判明し、XMPサイドカーファイル方式で回避
- 拡張子偽装ファイル(BMPを名乗るPNG等)を発見・修正
- Batch APIの処理停滞(93分、22分)を2度経験し、いずれもキャンセル操作が処理完了のトリガーとなり大半を無傷で回収
- Tier2最終: 6,094/6,094件(100%)完了

### Phase 3: 機種別フォルダへの再編成(9/20 15:24〜17:00)
- 移動対象27,388件の機種(Model)を全件実測し、新規10フォルダを含む再編成計画を確定
- テスト移動(100件)で移動ロジック・タグ保持を検証してから本実行
- 全27,388件をエラー0件で移動完了(所要時間 約2分15秒、ローカル処理のみのため高速)
- `.xmp`/`.aae`サイドカーファイルは親ファイルの移動先に追従させる設計を適用
- `_機種不明`フォルダに混入した非写真ファイル(.aae, .thm, Picasa管理ファイル等)を`_非写真`へ再隔離
- 空になった年別フォルダを削除し、最終的にフラットな構成を達成

## 6. 発生した主な障害と対応

| # | 障害 | 原因 | 対応 |
|---|---|---|---|
| 1 | OneDrive削除がごみ箱を経由せず完全削除に | 壊れたクラウド専用プレースホルダーに対しWindowsシェル削除がサイレントにフォールバック | 事前のハッシュ検証で実データを退避済みだったため実害なし。教訓として記録 |
| 2 | cuba1フォルダの重複相手を誤認 | 初期仮説(Xperia XZ_SOV34)が誤りで、実際は2008フォルダと重複 | 再検証により正しい重複関係を特定 |
| 3 | ファイル名連番リセットによる誤判定リスク | 別年に同名・同サイズの別写真が偶然存在(4.7%) | 全件ハッシュ照合に切り替え、統計的リスクを排除 |
| 4 | AAEファイルの高い誤判定率(11.5%) | 中身が小さいため偶然同サイズになりやすい | AAE全件を個別にハッシュ検証 |
| 5 | チェックポイント設計の未実装 | 「実装した」と報告していたが実際は反映されていなかった | リトライパス起動前にコードを再確認し修正 |
| 6 | 1,000件バッチの通信エラー(9回→27回→8,950件) | 1バッチ約200MBの大容量ペイロードが通信の不安定要因に | バッチサイズを200件に縮小し全件解消 |
| 7 | 実行中プロセスへのコード修正が反映されない | Pythonはホットリロードしないため、古いコードのまま動作継続 | プロセスを安全停止し修正版で再起動する運用に統一(2回発生) |
| 8 | exiftoolのBMP書き込み非対応 | ツール自体の仕様制限 | XMPサイドカーファイル方式で回避 |
| 9 | 拡張子偽装ファイル(BMPを名乗るPNG等) | 過去の何らかの操作でファイル名のみ変更されたと推定 | 実体を検証し正しい拡張子にリネーム |
| 10 | 真の破損JPEG(12件) | ファイル末尾のJPEG終端マーカー(2〜34バイト)のみ欠損 | 終端マーカー補完により無劣化修復 |
| 11 | Batch APIの長時間停滞(93分・22分) | 原因不明(Anthropic側の一時的な処理待ち、ステータスページ上の障害情報なし) | キャンセル操作が最終確定のトリガーとなり大半を無傷回収。ごく少数は個別送信に切替 |
| 12 | HEICがVision APIに直接送信不可 | 対応MIMEタイプ外(image/jpeg, png, gif, webpのみ) | pillow-heifでJPEG変換してから送信 |
| 13 | RAWファイルが画像ビューアで開けない | RAW形式はVision API・PIL共に非対応 | exiftoolで埋め込みJPEGプレビューを抽出して代用 |
| 14 | 32個のゾンビbashプロセスが蓄積 | 過去フェーズの「完了」通知後もプロセスが終了せず残留 | 不要な18プロセスを識別して停止。うち8件は「完了扱いだが実際は宙に浮いていた」ことが判明 |
| 15 | サイドカーファイル(.xmp/.aae)が親と分離するリスク | 独立に機種判定すると親写真と別フォルダに移動される恐れ | 親ファイルの移動先に追従させる設計に変更 |

## 9. 教訓・振り返り

1. **写真は撮り直せない。** 音楽整理では「最悪失っても入手し直せる」という前提があったが、写真整理では統計的リスクがわずかでも残る場合は必ず全件検証する方針が最終的に功を奏した(実際に4.7%・11.5%という無視できない誤判定率が判明した)。
2. **大容量ペイロードは通信の不安定要因になる。** バッチ処理では、件数だけでなくデータ量(MB単位)を意識したサイズ設計が重要だった。
3. **コードの修正は実行中プロセスには反映されない。** この教訓を得るまでに2度同じ種類の問題が発生した。修正時は必ずプロセスを再起動する運用に統一した。
4. **Batch APIの長時間停滞は、キャンセルが有効な回復策になり得る。** 2度とも、キャンセル操作自体が処理を完了扱いに導いた。
5. **「完了」報告を鵜呑みにしない。** ゾンビプロセスの調査により、過去に「完了」と報告されていた8件の処理が実際には宙に浮いていたことが判明した。定期的な健全性確認の価値を再認識した。
6. **対になるファイルの活用でコストと時間を大幅に削減できた。** RAW/HEICの約半数はJPEGペアからのタグコピーで済み、Vision API送信を回避できた。
